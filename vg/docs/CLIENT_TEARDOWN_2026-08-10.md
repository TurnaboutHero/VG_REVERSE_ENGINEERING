# 클라이언트를 뜯었다 — 어디까지 가고 어디서 막혔나

2026-08-10. `[18 04 03]` 의 영웅 고정 상수(1~60, 정수, Grumpjaw 16/14/20,
Caine 13, Kinetic 22.5)가 무엇인지 밝히려고 4.13.1 클라이언트를 열었다.
**값의 의미는 못 밝혔다.** 대신 어디에 있고 왜 못 읽는지가 확정됐다.

## 1.4GB 를 안 받고 구조부터 봤다

드라이브의 `Vainglory_4.13.1(1A)_Modified.xapk` 는 공개 링크이고 서버가
Range 요청을 받는다. `.xapk` 는 ZIP 이고 **ZIP 중앙 디렉터리는 파일 끝에
있으므로** 끝 4MB 만 읽으면 목록이 나온다.

| 항목 | 크기 | 저장 |
|---|---|---|
| `main.102880...obb` | 1,400,342,759 | 무압축 |
| `com.superevilmegacorp.game1.apk` | 33,510,768 | deflate |
| icon.png, manifest.json | 작음 | |

APK 만 33.5MB 받아 풀었다. OBB 가 무압축이라 xapk 안 바이트 주소가 곧 OBB
주소여서, OBB 도 받기 전에 안쪽 목록을 Range 로 읽을 수 있었다.

## APK 에는 데이터가 없다

630 항목이 png 350, xml 230. 큰 것은 엔진 `libGameKindred.so`(45MB)와
`classes.dex`. `assets/Data/Startup.ini` 는 서버 URL 만 담는다.

엔진 바이너리에서 건진 것: 스킬 식별자 체계. `Ability__Blackfeather__DefaultAttack`,
`Ability01_A`, `Buff_JungleMinion_Perk_NWScaling` 류 1,842개. **수치는 없다.**
영웅 이름 주변 ±4KB 의 float 을 훑어도 관측값과 맞는 게 Ardan 의 12·20 정도로
잡음 수준이다.

## OBB 는 내용 주소 저장소다

48,450 항목이 전부 32자 hex 이름(`0D/0D9EABC833E2EF3AB23BF310F529DF56`).
경로도 확장자도 없다.

**경로 MD5 가설을 검정하고 버렸다.** 엔진 바이너리에서 경로꼴 문자열
2,699개를 뽑아 6가지 변형(소문자, 구분자, 선행 슬래시)으로 MD5 를 때렸다 —
**0개 적중.** 내용 해시라 이름을 되돌릴 수 없다.

## 이름은 파일 안에 있었다

자산은 `CFF0` 매직으로 시작하는 청크 컨테이너다.

```
CFF0 | DEF0 | INST | ... | SYMB
```

`SYMB` 청크가 객체 이름을 `*이름*` 꼴로 담는다. 48,450개를 훑으면 해시 →
이름 색인 943개가 나온다.

그 색인 자체는 이 저장소에 두지 않는다. 클라이언트에서 뽑아낸 자료를 통째로
재배포하는 모양이 되기 때문이다. 만드는 방법은 위에 적힌 그대로이고 — OBB 를
열어 `CFF0` 로 시작하는 항목의 `SYMB` 청크에서 `*...*` 를 줍는다 — 필요하면
누구든 자기 사본에서 다시 만들 수 있다.

**CFF0 데이터 자산은 942개뿐이다.** 나머지 47,252개는 텍스처·오디오다.
1.4GB 중 실제 게임 데이터는 아주 작은 조각이라는 뜻이고, 다음에 뭘 찾든
이 942개만 보면 된다.

색인에 들어 있는 것들: `HeroManifest`, `Hero000`~`Hero062`, `Grumpjaw`,
`Blackfeather`, `Kensei`, `Talent_Blackfeather_Elusiveness`,
`Ability__Item__ReflexBlock`, `KindredHeroMasteryManifest`.

## CFF0 컨테이너는 풀었다

청크는 **태그(4) + 크기(4) + 페이로드**이고 크기는 헤더를 포함한다. 모든
파일에서 오프셋이 정확히 이어진다.

```
파일 머리 (u32 LE)
  +0  'CFF0'   +4 파일 크기   +8 2(버전)   +12 1798   +16 0
  +20 첫 섹션 오프셋(항상 64)   +24 둘째 섹션 오프셋

섹션 = DEF0(16) | INST | PTCH | SYMB      <- 파일마다 두 개
```

- `DEF0` 페이로드 8바이트: 타입 코드(첫 섹션 2054, 둘째 1287)와 상수 해시
- `SYMB` 페이로드: `u32 0 | u32 타입해시 | *이름* | 패딩`
  타입 해시는 이름 해시가 **아니다** — SAW 와 HeroPLU 가 같은 값을 쓴다
- `PTCH`: 첫 항목이 `(개수, 0)` 헤더, 이후 `(INST 안 오프셋, 목표 오프셋)`
  쌍. 오프셋은 4의 배수, 목표는 아니다. 재배치표다.

타입 해시로 942개를 가르면 이렇게 나온다.

| 타입 | 개수 | 내용 |
|---|---|---|
| 605682540 | 233 | 영웅·맵 객체 (`Grumpjaw`, `5v5_Blackclaw_Captured`) |
| 2707317498 | 189 | `Talent_*` |
| 4007347397 | 114 | 튜토리얼 사이드바 |
| 4235559905 | 94 | `Item_*` |
| 1767399352 | 59 | `GameMode_*` |
| 1468442026 | 8 | `Ability__*` (일반 스킬만) |
| 470098959 | 6 | `ItemStore_*` |

## 막힌 지점: INST 가 암호화돼 있다

청크별 바이트 엔트로피를 재면 갈린다.

| 청크 | 엔트로피 | 0바이트 |
|---|---|---|
| INST | **7.3 ~ 8.0** | 0.4% |
| PTCH | 4.4 ~ 4.5 | 51% |
| SYMB | 3.1 ~ 3.8 | 30% |

**압축이 아니라 암호다.** 근거는 크기다. `PTCH` 의 목표 오프셋이 `INST`
페이로드 크기 안에 정확히 들어온다(Item_Aegis: 페이로드 712, 최대 목표 700).
압축이라면 해제 후 주소가 압축 크기를 넘어서므로 맞을 수 없다. 크기 보존
변환이다.

쉽게 깨지지도 않는다.

- **반복 XOR 아님.** 자기상관에서 거리 33 이 7.6배로 튀지만 66·99·132 에
  배수 봉우리가 없다. 키 주기가 아니라 평문 구조의 반복이다.
- **키스트림 공유 아님.** 같은 타입 두 자산의 INST 를 XOR 하면 엔트로피
  7.51~7.71, 한 파일 안 두 섹션끼리 XOR 해도 7.24~7.99. 5 이하로 안 떨어진다.

청크마다 키가 다르다. 복호하려면 45MB ARM64 바이너리에서 루틴을 찾아야 하고,
그건 디스어셈블러를 놓고 하는 별개 작업이다.

## 아는 답으로 들어가려다 안 된 것

영웅 스킬 수치는 정답을 모르니 **아이템 가격**으로 스키마를 뚫으려 했다.
Item_* 94개는 타입이 같으니 구조도 같고, 가격이 놓인 오프셋은 여러 아이템에서
같아야 한다.

- 고정 오프셋 정렬: **0건**
- 그래서 물었다 — 가격이 파일 안에 있기는 한가. **72개 중 66개가 어떤
  인코딩으로도 안 나온다.** 아이템 자산에 가격이 없다.
- 가격은 상점에 있다: `ItemStore_Standard_3v3` 40/72, `ItemStore_Standard_5v5`
  34/72, `KindredItems` 29/72

상점 자산도 INST 가 암호화돼 있어 같은 벽에 막힌다. 공식 가격표를 뽑으면
디코더가 리플레이에서 역산한 가격표를 외부 근거로 검증할 수 있었을 텐데,
거기까진 못 갔다.

## 헛짚은 것 하나, 그리고 그 정체

Grumpjaw 자산 +89034~+89170 에 14.0, 14.0, 16.0, 20.0 이 140바이트 안에
몰려 있어 스킬 표인 줄 알았다. 값을 나열하면 (0.59, 0.78), (0.81, 1.00),
(1.19, 1.56), (1.75, 2.63) … 처럼 단조 증가하는 쌍이라 곡선 보간표로 보였다.

컨테이너를 풀고 나니 정체가 확실해졌다. **그 자리는 두 번째 `PTCH` 안이다**
(+84144 ~ +95120). 평문 오프셋 쌍을 float 으로 읽으면 그런 매끄러운 수열이
나온다. 스킬 표도 곡선표도 아니었고, 관측값과 같은 숫자가 나왔다는 것만으로는
아무것도 아니었다.

## 비용 대비

여기서 멈춘다. 끝까지 밀어도 얻는 것은 **상수의 이름**이고 디코더 정확도는
움직이지 않는다. `[18 04 03]` 의 값은 지금 쓰는 곳이 없고 영웅 판정은 이미
바이너리 ID 로 100% 다.

다시 붙는다면 순서는 이렇다: `libGameKindred.so` 에서 CFF0 로더를 찾아
INST 복호 루틴을 뽑는다 → 상점 자산을 풀어 공식 가격표를 얻는다(이건 디코더에
실익이 있다) → 그 다음에 영웅 자산.

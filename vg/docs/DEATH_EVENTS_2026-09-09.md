# 사망 액션 검증 (2026-09-09 KST)

## 결론

`0x0430`은 검사한 Windows 실행 파일에서 실제 `Nuo::Kindred::ActionActorDie`를 생성하는 사망 액션이다. `0x041c`의 데스 카운터 증가와 구별되는 독립 액션을 확인했다. `0x0431`은 별도 조건부 상태 전환이며 사망 사건 자체로 이름 붙이지 않는다.

## 직접 만든 연습 경기

대응 플레이어 entity ID는 1500이다. strict-framed 기록에서 다음 순서를 확인했다.

| 항목 | 기록 시각(초) | 앵커 환산 게임 시각(초) |
|---|---:|---:|
| `0430`, 사망 개체 1500, 원시 source 2007 | 978.115417 | 976.770081 |
| `041c`, attribute 42/layer 0/ADD 1 | 978.115417 | 976.770081 |
| `0431`, 개체 1500 상태 전환 | 979.934875 | 978.589539 |

`0430` 본문: `000005dc000007d7000000000000`. `041c` 본문: `000005dcffffffff3f8000002a000000000000000000`.

`0431`은 데스 증가보다 약 1.819458초 늦다. `041c.ref1`은 `ffffffff`이며 이 칸을 가해자 ID로 해석할 근거는 없다. 독립 액션 `0430`의 두 번째 참조와 혼동하지 않는다.

화면에서는 연속 캡처 마지막 `16:01`에 KDA 0/0/0, 별도 `16:20` 이미지에 쓰러진 영웅·부활 카운트다운·KDA 0/1/0, 결과 `20:07`에 0/1/0을 직접 확인했다. 사망 순간은 10분 연속 캡처의 제한 이후여서 빠져 있다. 따라서 위 소수점 시각은 파일 시각이며 화면 전환의 정밀 시각으로 검증된 값이 아니다. 후속 정의 조회에서 source 2007을 `VainCrystal_Away_5v5`로 확인했다. 아래 구조물 분류를 참조한다.

## native 경로

실행 파일 SHA256과 주소는 [manifest](evidence/2026-09-09-death/manifest.json)에 기록했다.

1. [dispatcher](evidence/2026-09-09-death/dispatcher-excerpt.txt)는 `0430`에서 앞 8바이트를 두 BE32 값으로 읽고 `00819f30`을 호출한다.
2. [생성자](evidence/2026-09-09-death/decompiled-00819f30.c)는 이 값을 객체 +0x10/+0x14에 보존하고 `ActionActorDie` vtable을 설정한다.
3. [vtable](evidence/2026-09-09-death/vtable.txt)의 +0x0c [복사 경로](evidence/2026-09-09-death/decompiled-0092d7d0.c)는 두 값을 보존해 큐에 넣는다.
4. +0x08 [apply](evidence/2026-09-09-death/decompiled-0094c8f0.c)는 첫 번째 값으로 actor를 조회하고, 해당 actor와 두 번째 참조를 알림·HUD에 전달한다.
5. [알림](evidence/2026-09-09-death/decompiled-00541430.c)은 `HeroKilled`, `YourKill`, `TurretDestroyed` 등에 연결된다. [전투 로그](evidence/2026-09-09-death/decompiled-005b19e0.c)는 hero/turret/minion/목표물 아이콘과 `hud_stats_kills`를 사용한다.

두 번째 참조는 death source로 사용되지만 HUD가 다른 actor 참조 또는 소유자 경로를 통해 대체하는 코드가 있다. 원시 source와 최종 킬을 인정받은 영웅을 동일시하지 않는다. 스킬·피해 유형·어시스트 참여자 목록은 이 두 필드로 확인되지 않았다. `0430`은 플레이어만의 이벤트가 아니므로 피해 개체 분류가 필요하다.

## 검증 범위

기존 파일을 읽고 실행 파일을 오프라인 분석했다. 게임 재실행·후킹·원본 리플레이 변경은 하지 않았다. 제품 타임라인의 기본 opcode 목록이나 최종 집계 정책은 수정하지 않았다. [직접 경기 레코드](evidence/2026-09-09-death/direct-death.json)와 원시 자료와 분석 스크립트는 비공개 작업 폴더에 보관했다. 이 문서와 함께 익명화한 결과 및 필요한 native 발췌를 공개한다.

## 56개 코퍼스 교차 검증

플레이어 ID는 기존 parser에서 읽고, layer 0의 attribute 42 ADD 1만 데스 증가로 세었다. 초기 스냅샷이나 SET은 제외했다. 모든 opcode 탐색은 strict framing으로 했다. 코퍼스의 시계 상태는 그대로 보존했으며 지원되지 않는 시계를 이 조사로 승격하지 않았다.

- 플레이어 데스 증가 2,182건 중 2,157건은 같은 피해자·같은 기록 시각의 `0430`과 대응했다.
- 나머지 25건은 같은 피해자의 유일한 미대응 `0430` 뒤 0.008911~0.080444초에 증가가 있었다. 100ms 창으로 두 번째 비교를 했으며, 이 창은 형식 보장이 아닌 이번 분석 기준이다.
- 플레이어 대상 `0430`은 총 2,221건이다. 위 대응 외의 39건에는 검사한 layer-0 ADD-1 증가가 없었다. 모두 종료 액션 0.119019~5.812500초 전에 있다. 다른 연산·서버 집계·결과 고정 시점 가운데 무엇이 원인인지는 이 비교만으로 확정하지 않는다.
- source가 플레이어 ID인 2,075건 중 2,005건은 해당 source의 킬 ADD-1과 정확히 같은 기록 시각이었다. 나머지를 킬 귀속 오류라고 단정하지 않으며, 소유자/대체 참조와 시각 차이는 별도 검증 대상이다.
- 코퍼스에서 `0430`의 payload 길이는 14바이트였다. native dispatcher가 읽는 앞 8바이트 이외를 의미 없이 버리거나 해석하지 않는다.

따라서 `0430`을 **사망 액션 사건**으로 식별하는 근거는 확보했다. **최종 데스 = 0430 개수**라는 규칙은 적용하지 않는다. 스코어 카운터, 액션 전달, 화면 표시, 최종 집계는 구별해야 한다.

근거: [코퍼스 집계](evidence/2026-09-09-death/corpus.json), [추가 시각 대응·종료 전 예외](evidence/2026-09-09-death/correlation-summary.json). C번호는 기존 종료 조사와 같은 익명 코퍼스 순번이다. 실제 사망 프레임의 정밀 화면 대조와 어시스트·스킬 원인은 미확인으로 남긴다.


## 사망 원인 구조물 분류

직접 경기의 원시 사망 원인 ID **2007**은 `03f2` 생성 레코드에서 정의 번호 **296**을 사용한다. 121개 섹션에서 같은 매핑을 확인했다. 설치된 같은 Windows 클라이언트의 `Levels/DefinitionManifest.def`를 native CFF `INST` 변환·`PTCH` 복원 방식으로 읽으면 32비트 정의 배열의 296번이 **`VainCrystal_Away_5v5`**다.

| 정의 번호 | 이름 |
|---:|---|
| 295 | VainCrystal_Home_5v5 |
| 296 | VainCrystal_Away_5v5 |
| 297 | VainNode |
| 339 | Turret5v5 |
| 340 | OuterTurret5v5 |
| 341 | ArmoryTurret5v5 |

따라서 이 사례는 **베인 크리스탈 사망**으로 분류한다. `2007`이나 정의 번호를 다른 경기·다른 클라이언트에 고정하지 않는다. 특정 A/B 공격·마지막 피해량까지는 검증하지 않았다.

[생성 매핑·리소스 해시·정의 배열 발췌](evidence/2026-09-09-death/source-type-proof.json), [생성자](evidence/2026-09-09-death/decompiled-0081a750.c), [정의 인덱스를 사용하는 apply](evidence/2026-09-09-death/decompiled-0094d480.c), [CFF 로더](evidence/2026-09-09-death/decompiled-0112c820.c), [INST 변환](evidence/2026-09-09-death/decompiled-011412d0.c).

재현 시 합법적으로 보유한 동일 빌드의 리플레이·실행 파일·리소스를 사용하고 공개 해시와 비교한다. `0430`의 두 BE32 참조를 읽고, source에 대응하는 `03f2`의 첫 번째/세 번째 BE32(정의 인덱스/개체 ID)를 연결한다. Manifest의 32비트 `INST`에 native 변환을 적용한 뒤 `PTCH`의 위치/대상 오프셋 쌍을 복원한다. 직렬화 루트의 배열에서 해당 인덱스의 항목과 첫 문자열 참조를 읽는다. 실행 파일·리소스 전체와 원본 리플레이는 저장소에 포함하지 않는다.

## 제품 반영 상태

이 커밋은 발견과 검증 근거를 공개한다. 기존 타임라인은 `--opcode 0x0430`으로 원문을 추출할 수 있지만 `0430` native 라벨·source 종류 조회를 제품 기능으로 추가하지는 않았다. 기본 목록에도 아직 포함되지 않는다. 구현·회귀 검증과 최종 집계 경계 실험은 [다음 계획](../../docs/plans/2026-09-09-event-semantics-next.md)에 분리했다.

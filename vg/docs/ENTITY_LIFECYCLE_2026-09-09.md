# 개체 삭제 액션과 수명 관찰

`040b`는 검증된 Windows 빌드의 `Nuo::Kindred::ActionEntityDestroy`다.
기록에 이 액션이 있다는 사실과 실제 개체 삭제가 완료된 시각은 구별한다.
`0430` 사망 액션이나 `0431` 상태 전환만으로 개체 수명을 끝내지 않는다.

## 네이티브 근거

사용자가 보유한 PE32 실행 파일의 SHA-256은
`659f9eed557a426db57554d2a768efe34ba9fe02ba1085d77db64390b0d92642`다.
아래 주소는 image base `00400000`을 포함한 Windows VA다.
기존 Ghidra 프로젝트를 `-readOnly -noanalysis`로 열었으며 실행 파일과
프로젝트의 해시가 같음을 확인했다. 게임 바이너리와 리소스는 포함하지 않는다.

| 경로 | 확인된 동작 |
|---|---|
| Dispatcher `004cfec0`, 호출 `004d2427` | `040b` 본문 첫 4바이트를 네트워크 순서 uint32 ID로 읽고 `0081a6c0`을 호출한다. |
| 생성자 `0081a6c0`, vtable `0127c848` | `ActionEntityDestroy`의 ID를 action+`0x10`에 보관한다. |
| Apply `0094d470` / 생성자 경로 `0092b630` | ID를 조회하고, 있으면 `onBeforeActorDestroyed` 콜백과 `0112a1f0`을 호출한다. |
| `DAT_0209e204` | 0이면 apply 경로, 0이 아니면 생성자의 즉시 처리 경로를 선택한다. 이 플래그 때문에 한쪽 모드가 액션을 모두 버린다는 뜻은 아니다. |
| `0112a1f0` | 개체 풀의 bitmap에 정리 대상 비트를 설정한다. 함수 안에서 곧바로 메모리를 해제하지 않는다. |
| 조회 `00857970` | `FFFFFFFF`는 개체 조회에 성공하지 않는다. |
| 생성 apply `0094d480` / `0094e170` | 같은 ID가 이미 있으면 새 개체 생성을 생략한다. 반복 생성 기록은 재스폰의 증거가 아니다. |

기록 시각은 바깥 레코드의 시각이다. 큐 적용·콜백 실행·풀 정리가 끝나는
시각으로 해석하지 않는다. 생성된 개체의 생존 여부, ID 재사용, 소유자 또는
킬 인정 플레이어를 이 액션 하나로 정하지 않는다.

## 실제 기록 대조

기존 직접 연습 경기의 121개 섹션, 300,667개 레코드를 다시 읽었다.

- `040b`: 1,242건 모두 **본문 6바이트 / content length 8**이다.
  첫 4바이트만 ID로 해석하며 마지막 2바이트는 원문 그대로 보존한다.
- 1,242개 ID 모두 이전 생성 관찰이 있었다. 중복 삭제 액션이나 삭제 뒤
  같은 ID의 생성 관찰은 이 기록에서 없었다.
- 생성 관찰은 16,061건, 서로 다른 ID는 1,375개다. 1,340개 ID가 반복됐으나
  같은 섹션 안 반복이나 정의 변경은 없었다. 스냅샷과 일치하는 패턴이며
  다른 모든 기록의 생성이 스냅샷이라는 증거는 아니다.
- 예시: 섹션 5, offset 43479, 기록 시각 약 54.820초, ID 2679의 삭제 액션.
- 삭제 뒤 검증된 다른 opcode 참조가 남은 ID는 3개다. 첫 사례는 ID 70036,
  섹션 83의 삭제 offset 35581 뒤 `042b` offset 35597이다. 따라서 삭제
  관찰 뒤 참조를 버리면 실제 기록을 손실한다.

따라서 삭제 뒤 재등장·정의 변경·중복 삭제·선행 생성 없는 삭제는 합성 입력으로
검증한다. 실제 코퍼스에서 재스폰이나 ID 재사용을 관찰했다고 보고하지 않는다.

## 출력의 의미

카탈로그 모드의 identity는 과거 생성 이름과 원시 바이트를 계속 보존한다.
별도의 lifecycle 근거에 최신 생성/삭제 액션 관찰을 연결한다. 삭제 뒤 생성은
`spawn_after_destroy_observation`으로 표현하며 `respawn`으로 단정하지 않는다.
원시 삭제 행은 `--opcode 0x040b`로 선택한다. 기본 opcode 목록은 유지한다.

```text
python -m vg.analysis.event_timeline replay.0.vgr --opcode 0x040b --entity 2679
```

카탈로그·빌드 인자를 추가하면 이름과 수명 관찰 근거가 함께 나온다.
`--opcode`나 `--entity` 필터에 가려진 삭제 액션도 뒤에 나오는 참조의 근거에
반영된다. 카탈로그 모드에서 미검증 본문 길이는 거부한다.

이 확장은 최종 KDA, 완료 판정, winner 또는 broad kind를 바꾸지 않는다.
두 개체 종류의 화면 대조와 비항복 종료 결과 화면은 별도 미완료 검증이다.

## 구현 검증

Windows에서 전체 359개 테스트가 37.882초에 통과했다. private truth fixture는
검증용 사본만 잠시 제공한 뒤 제거했고, tracked cache는 변경되지 않았다.
CLI `--help`, 정상 입력, 필터에서 제외된 잘못된 삭제 본문의 exit 2를 확인했다.

실제 CLI는 1,242개 삭제 행 모두에 수명 관찰 근거를 출력했다. ID 70036의
`042b` 후속 행은 과거 이름 `5v5_Minion_Range`와 삭제 offset 35581을 함께
보존했다. 기존 크리스탈 사망 20개 행의 원시 출력은 이전 출력과 동일했고,
이름·수명 envelope를 제거한 값도 동일했다. 실행 전후 121개 원본 섹션과
실행 파일·manifest의 SHA-256은 변하지 않았다.

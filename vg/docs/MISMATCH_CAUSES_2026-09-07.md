# 왜 결과 화면과 100% 일치하지 않았나

2026-09-07. **불일치는 하나의 잘못된 킬 판정 규칙 때문이 아니었다. 비교 시점, 시작 통계, 시간 기준, 입력 파일 구성에 서로 다른 문제가 있었다.**

이번에는 숫자를 결과에 맞춰 보정하지 않고, 원본 레코드·초기 스냅샷·각 파일의 시간 기준·기준 이미지·Android APK의 수신 코드를 함께 확인했다. 원본 리플레이와 기존 truth JSON은 변경하지 않았다.

## 확인된 원인 세 가지

| 경기 | 실제 원인 | 관측 결과 |
|---|---|---|
| M5: 결승 1경기 | 기준 이미지는 경기 중 18:55 점수판인데, 그 뒤의 기록까지 합산했다. | 기존 불일치 4개가 해당 시점 대조에서는 모두 사라진다. |
| M6: 결승 2경기 | 기록 시작 전에 쌓인 통계를 빠뜨렸고, 기록의 0초를 게임의 0초로 취급했다. 기준 이미지도 최종 결과가 아닌 25:51 점수판이다. | 시작값만 반영하면 불일치 11→4개, 시계만 맞추면 11→7개, 둘 다 반영하면 0개다. |
| M9: 결승 5경기, Incomplete 폴더 | 같은 파일 번호 묶음 안에 게임 초반과 후반 상태가 섞여 있다. 파일 번호 순서가 게임 시간 순서가 아니다. | 시계가 두 번 약 18분 31초 뒤로 돌아가고 통계도 초기 상태로 되돌아간다. 최종 점수 검증 대상으로 사용할 수 없다. |

장부로 비유하면 M5는 **중간 결산표와 나중 장부를 비교**했고, M6는 **이월 금액과 시계 차이를 빠뜨렸으며**, M9는 **서로 다른 시점의 장부 페이지가 섞여 있었다.**

## M5: 최종 결과라고 생각했던 이미지가 중간 점수판이었다

원본 이미지를 직접 확인했다. 시각은 18:55이고 항복·닫기 버튼, 사망 대기 시간, 아이템 재사용 대기 시간이 있다. 최종 승패 결과 화면이 아니다.

추가 킬·사망·어시스트 기록은 파일 시각 1147.601929초에 있다. 그 파일의 시간 기준으로 환산해도 화면의 1135초 이후다. 자원14 증가 1건도 화면 이후다. 화면이 찍힌 시점을 기준으로 대조하면 기존 9명에서 비교하던 KDA와 CS 값 36개가 전부 맞는다.

이는 해당 이벤트가 가짜라는 뜻이 아니다. **화면을 찍은 뒤에 실제 통계가 더 바뀌었는데, 앞서 찍은 화면을 경기 끝의 정답으로 사용한 문제**다. 이 화면만으로 경기 최종 승자도 확정할 수 없다.

## M6: 시작값과 두 시계를 함께 처리해야 했다

게임은 각 리플레이 조각에 현재 상태 스냅샷(`0x03F3`)을 남긴다. 그 안에는 이미 쌓인 통계도 있다. Android APK의 실제 수신 코드에서 다음 연결을 확인했다.

| 스냅샷 payload 위치 | 적용되는 통계 |
|---|---|
| 298 | 능력치41, 킬 |
| 302 | 능력치42, 사망 |
| 306 | 자원11, 어시스트 |
| 310 | 자원14, 이번 자료의 CS와 대조한 값 |

스냅샷은 증가량이 아니라 **현재 값의 대입**이다. 따라서 매 조각의 스냅샷을 더해서도 안 되고, 첫 시작값을 무시해서도 안 된다. 수신 코드의 통계 생략 플래그(payload326)도 확인하고 적용했다. 자원14의 저장 경로는 확인했지만 게임 코드의 CS 표시 이름까지 독립적으로 추적한 것은 아니다.

M6은 파일 시각 0초에 시간 기준 값이 이미 **85.893326초**다. 시작 통계에는 자원14가 4·6·7·8처럼 0이 아닌 플레이어가 있다. 예를 들어 한 플레이어는 처음부터 6이 있었는데 이후 증가분 160만 세어 166인 화면과 맞지 않았다.

또한 파일의 레코드 시각은 **녹화 기준 시각**이며 화면의 경기 시각과 같은 값이 아니다. 지난 작업에서 다음 레코드의 시각을 잘못 읽는 문제는 고쳤지만, 그것만으로 화면 시각과의 변환까지 해결한 것은 아니었다.

각 파일의 `0x046F`에는 별도 float 시간 기준이 있다. 이를 받아 게임 객체에 저장하는 경로를 APK에서 확인했다. 이번 대조에서는 그 기준과 파일 내 경과 시간을 사용했다. 화면 시계 렌더링 함수까지 추적한 증명은 아니므로, 보간된 시간을 프레임 단위의 정확한 사건 시각으로 주장하지 않는다.

M6 마지막 부근에서는 파일 시각1460.001초가 시간 기준1545.911초에 대응한다. 그러므로 25:51 화면을 파일 시각1551초까지 합산해서는 안 된다. 뒤의 파일 시각1484.379초 킬·사망은 화면 시각으로 약1570초이며 화면 이후다.

원인별 재현 결과:

| 읽는 방법 | M6의 비교 가능한 값36개 중 불일치 |
|---|---:|
| 시작값 없이 모든 증가분 합산 | 11 |
| 시작값만 반영하고 모든 증가분 합산 | 4 |
| 시작값 없이 화면의 시계만 맞춤 | 7 |
| 시작값과 화면의 시계를 모두 반영 | **0** |

처음 스냅샷에서 시작해 증가분을 누적한 계산과, 비교 시점에 가장 가까운 조각의 스냅샷에서 다시 시작한 계산이 모두 같은 값을 냈다. 화면에 표시된 초의 시작과 끝에서도 비교 값은 변하지 않았다. 경기별 보정 상수를 결과 숫자에서 찾아 넣은 것이 아니다.

## M9: 파일의 실제 내용이 시간순으로 이어지지 않는다

파일 번호는 0~84로 빈 번호 없이 있다. 레코드 헤더의 시각도 파일 번호에 맞게 증가한다. **그래서 파일 개수나 레코드 형식만 검사하면 문제를 놓친다.**

그러나 조각 안의 시간 기준과 통계는 다음과 같다.

| 조각 전환 | 조각 안의 시간 기준 변화 |
|---|---|
| 6 → 7 | 1179.091초 → 68.004초 |
| 9 → 10 | 88.006초 → 1219.104초 |
| 32 → 33 | 1439.099초 → 328.005초 |

동일 캐릭터의 초기 상태도 후반 상태에서 초반 상태로 되돌아간다. 원본 파일 수정 시각 역시 0~6·10~32번이 다른 구간보다 나중인 별도 묶음으로 나타난다. **서로 다른 녹화 시점의 조각이 함께 있는 구성**이라는 근거다. 누가 어떤 프로그램으로 그렇게 저장했는지는 확인하지 않았다.

이 자료를 한 경기의 연속된 이벤트로 합산하면 일부 구간은 빠지고 일부는 엉뚱한 시작값에 더해진다. 시작 스냅샷을 추가하는 것만으로도 해결할 수 없다. 최종 화면의 28:29 시점도 현재 조각으로 정상적으로 이어서 확인할 수 없다.

처음에 ‘850초밖에 없으므로 뒤가 잘렸다’고 해석한 것은 성급했다. **기록 시계가 경기 시계와 다르고 서로 다른 구간까지 섞여 있으므로 단순 길이 비교로 누락 방향을 판단할 수 없다.**

복구 가능성을 확인하려고 기존 리플레이 루트의 ZIP41개와 저장소의 자료 폴더를 검색했다. 같은 경기를 담은 보관 ZIP에서 찾은85개 조각은 현재85개 파일과 SHA-256이 전부 같았다. 즉 이번 조사 중 파일을 바꿔서 생긴 현상이 아니며, 확인한 보관본에도 같은 구성이 있다. 검색한 범위에서 정상 대체본은 발견하지 못했다. 다른 기기나 외부 백업의 존재까지 배제한 것은 아니다.

## 다시 대조한 결과와 정확한 범위

| 항목 | 결과 |
|---|---:|
| 시간 구성이 일관된10경기의 기존 비교 대상98명 KDA | **294개 값 전부 일치** |
| 같은10경기의 기존 CS 비교 대상 | **78개 값 전부 일치** |
| M9의 기존 KDA 비교 대상9명 | 27개 값을 검증 불가로 분리 |
| M9의 기존 CS 비교 대상 | 9개 값을 검증 불가로 분리 |

**전체 자료의 정확도가100%가 됐다는 뜻은 아니다.** M9을 고쳤다고 계산하지 않았으며, 최종 점수를 생성하지 않았다. 나머지10경기에서 이번에 확인한 비교 시점과 필드가 일치한다는 결과다. M5·M6은 최종 결과가 아니라 화면 촬영 시점의 일치다. 골드·아이템·승패·모든 이벤트·실제 사망/부활 프레임까지 검증한 것도 아니다.

기존 표의107명은110명 전원을 뜻하지 않았다. M5은 이미지에 보이는 한 명의 행이 JSON에서 빠져 있고, M6은 이름 철자 차이, M9은 I/1 이름 표기 차이로 엄격한 이름 매칭에서 각1명씩 빠진다. 이번 수치도 비교 기준을 바꾸지 않기 위해 기존107명 분모를 명시적으로 유지했다. 추가 행은 별도 근거 확인 뒤 반영해야 하며, 없는 행을0으로 계산하지 않았다.

## 무엇을 바로잡았고 다음 구현에 무엇이 필요한가

이번에는 **원인을 재현하는 읽기 전용 대조 도구와 증거 보고서**를 만들었다. 원본·truth·기존 운영 계산기는 변경하지 않았다. 기존 테스트263개 통과 기록을 이번 통계의 새 증거로 재사용하지 않았다.

다음 계산기 변경은 규칙을 더 추측하는 것이 아니라 다음 확인된 요구를 적용하는 작업이다.

1. 스냅샷의 시작 통계를 읽고 이후 SET/ADD를 적용한다. 조각별 스냅샷은 대입으로 처리한다.
2. 파일 시각과 경기 시각을 구분하고, ‘중간 화면’과 ‘최종 결과’의 비교 시점을 구분한다.
3. 게임 시계가 뒤로 이동하거나 다른 구간으로 점프하면 연속 경기로 계산하지 않는다. M9 같은 입력은 이유와 함께 검증 불가로 표시한다.
4. 원본 결과 자료에 화면 종류·촬영 시각·이름 연결 근거를 남긴다. M9은 정상적인 원본 구간이나 다른 백업이 있어야 최종 검증을 진행할 수 있다.

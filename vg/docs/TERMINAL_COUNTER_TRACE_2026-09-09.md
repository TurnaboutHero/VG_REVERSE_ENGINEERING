# 종료 직전 카운터 공백의 네이티브 경로 확인

종료 직전 39개 사망 액션의 누락 증가분은 여전히 **기록된 통계 갱신의 공백**이다.
이번 조사만으로 서버의 집계 중단 원인을 확정하거나 최종 데스를 보정하지 않는다.

검증한 Windows 실행 파일 SHA-256은
`659f9eed557a426db57554d2a768efe34ba9fe02ba1085d77db64390b0d92642`다.
주소는 Windows VA이며 image base는 `00400000`이다. Ghidra read-only 추출과
필요한 구간의 기계어를 대조했다.

## 확인한 경로

- `041c`: vtable `0127c9a0`, apply `0094f1d0`. SET/ADD는 `0095c710`을 거쳐
  `0095c590`에서 선택한 layer 배열에 float를 쓴다. K/D index 41/42를
  경기 종료 때문에 건너뛰는 조건은 이 경로에서 발견되지 않았다.
- `041d`: vtable `0127c9b4`, apply `0094f210`. 상태 3/4에 따른 ADD 제한은
  개별 actor의 resource 0/2에만 적용된다. assists 11과 CS 14는 이 제한을
  통과해 `0095f270`에서 저장된다.
- `ActionActorDie`의 상태 3/4 조건은 개별 actor FSM에 대한 조건이다.
  `0092c110`은 actor 상태를 3으로 바꾸고 `onActorDie` 콜백을 호출한다.
  별도 경기 FSM의 숫자 3과 같은 의미로 취급하지 않는다.
- 수신 dispatcher `004cfec0`은 opcode별 적용 전에 `004cb590`으로 원문을
  기록한다. 확인한 wrapper는 `041c/041d`나 K/D/A/CS index를 배제하지 않는다.
  따라서 뒤에 실행되는 HUD/apply guard만으로 이미 수신된 통계 패킷이 파일에서
  사라졌다고 설명할 수 없다.

## 기존 39건의 저장된 분석 재검산

원 분석 JSON의 SHA-256은
`030740b19301b9ba61a6ff7e46e4c8903acf66e954bc5040aa31a1fd140d8802`다.
이 항목은 저장된 분석의 재검산이며 전체 원본 코퍼스를 새로 읽은 결과와 구분한다.

- 28개 recording의 39건 모두 이후 플레이어 K/D/A/CS 연산이 0건이다.
- 뒤에 피해자 스냅샷이 있는 11건도 기존 death 값을 유지한다.
- 39건 모두 이후 피해자 상태 기록은 존재한다.
- 사망 액션은 `03f1`보다 기록 순서와 timestamp 모두 앞서며, 차이는
  약 0.119~5.813초다.

서버의 통계 생성 코드, 상위 수신 경로, 콜백 본문, 원본 recording의 빌드 일치,
최종 결과 화면은 미확정이다. 기록된 SET/ADD와 스냅샷을 보존하고, 사망 액션마다
데스를 더하거나 `03f1`에서 무조건 잘라내는 규칙을 추가하지 않는다.
독립적인 비항복 종료·최종 KDA 화면 대조가 다음 검증이다.

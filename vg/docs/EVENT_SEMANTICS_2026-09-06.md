## 쉽게 말하면

게임 기록에는 ‘누가 죽었다’처럼 바로 읽을 수 있는 문장뿐 아니라 ‘이 숫자를 1 올려라’, ‘이 숫자를 0으로 바꿔라’, ‘상태를 다음 단계로 옮겨라’ 같은 명령이 있다. 예전에는 이것들을 지나치게 단순한 사건 이름으로 읽고 있었다.

이번에 추적한 네 종류는 다음과 같다. 영어로 된 게임 내 이름까지 모두 알아낸 것은 아니지만, 내부 코드에서 수행하는 연산은 구체적으로 좁혔다.

| 기록 | 내부 코드에서 확인한 동작 | 아직 단정할 수 없는 것 |
|---|---|---|
| `0x041C` | 선택한 능력치의 값을 바꾸거나 더한다. 능력치 번호와 적용 층, SET/ADD 표시가 있다. | 모든 능력치 번호의 게임 내 이름, 보조 참조의 뜻 |
| `0x041D` | 선택한 자원·카운터의 값을 바꾸거나 더한다. SET은 `max(값,0)`, ADD는 `max(기존값+값,0)`인 경로가 있다. | 각 번호의 전체 의미, 일부 상태별 예외와 보조 플래그 |
| `0x042B` | 인덱스별 상태 비트와 두 마스크를 갱신한다. | 각 비트가 시야·행동·다른 무엇을 뜻하는지 |
| `0x0431` | 조건을 확인한 뒤 캐릭터의 숫자 상태를 3에서 4로 바꾼다. | 상태 3·4의 정확한 이름, 사망 발생 순간과 동일한지 |

고정된 공개 C 분석 자료에 더해, 현재 커뮤니티 변조·재배포 VG:NA 배포본의 GameKindredEngine 실행 코드에서 생성자·직렬화·가상함수 테이블·수신 처리 경로를 대조했다. 네 opcode의 실제 함수 연결과 관련 기계어 18개 구간을 확인했다. 단, 원본 전체 빌드 번호가 147219라는 것과 모든 로컬 리플레이가 같은 빌드에서 생성됐다는 것까지 입증한 것은 아니다.

## 킬·사망·어시스트 이름까지 확인한 연결

게임 내부에서 현재 캐릭터를 찾아 통계 객체로 내보내는 코드가 다음 값을 직접 읽는다. 단순히 이름이 비슷한 문자열을 발견한 것이 아니라, 캐릭터 메모리의 값이 해당 이름의 출력으로 전달되는 경로를 확인했다.

| 게임이 내보내는 이름 | 실제 내부 필드 | 해당 변경 기록 |
|---|---|---|
| `myKills` | 계산된 능력치 41 / 0x29 | 0x041C, index 41 |
| `myDeaths` | 계산된 능력치 42 / 0x2A | 0x041C, index 42 |
| `myAssists` | 자원 11 / 0x0B | 0x041D, index 11 |

킬·사망의 계산식은 `clamp((layer0 + layer1 × (layer3 + 1)) × (layer2 + 1), min, max)`다. 따라서 다른 층을 무시하거나 SET 기록을 사건 한 번으로 세면 안 된다. 새 타임라인은 이름, 층, SET/ADD, 원본 값을 모두 보존하며 최종 점수를 임의 계산하지 않는다.

56개 리플레이의 플레이어 기록을 별도로 확인한 범위에서는 위 세 통계가 모두 +1 ADD이고, 킬·사망은 layer0였다. 킬 변경 2,192건, 사망 변경 2,182건, 어시스트 변경 3,633건이다. 이것은 보유 자료에서 관찰한 분포이며 미래 모든 기록의 제약도, 최종 경기 합계의 정답도 아니다. 앞서 사망 후보로 세던 0x0431 2,209건과 직접 사망 통계 변경 2,182건도 구분한다.

자원 9·10은 여전히 다른 값이다. 킬·사망과 함께 움직여도 이 출력 코드가 그 둘을 직접 읽지는 않으므로, 같은 이름으로 합쳐 쓰지 않는다.

## 합계만 세면 놓치는 차이

예를 들어 `+1, +1, 0으로 바꾸기, +1`은 메시지 네 개지만, 현재 값은 1이다. 그렇다고 실제 행동이 한 번뿐이었다고 할 수도 없다. 누적 횟수와 연속 횟수가 서로 다를 수 있기 때문이다.

원본에서도 자원 번호 `0x09`, `0x0C`, `0x0F`를 0으로 바꾸는 기록이 발견됐다. 같은 캐릭터의 `0x0A` 값이 1 올라가는 시각과 겹치는 사례가 있다. 따라서 모든 메시지를 독립 사건으로 세거나, 마지막 자원 값을 그대로 최종 통계로 쓰면 안 된다.

기존 골드 코드가 `sell_flag`라고 부르던 바이트는 이 native 경로에서는 SET/ADD 선택에 해당한다. 이것은 기존 명칭의 문제를 드러내지만, 로컬 골드 공식 전체가 얼마나 달라지는지까지 이번 관찰 하나로 단정하지 않는다.

## 사망 시각과 뒤따르는 상태 변경

실제 M1의 한 캐릭터는 다음 순서였다.

```text
151.918초: myDeaths에 연결된 능력치 0x2A에 +1
     ↓ 약 1.838초
153.756초: 상태 3 → 4에 대응하는 0x0431
```

11개 비교 경기의 플레이어 `0x0431` 후보 301건 중, 같은 캐릭터의 가장 가까운 자원 `0x0A` 증가와 비교 가능한 것은 300건이었다. 그중 294건은 증가 뒤 1.604~1.942초 사이에 나타났다. 11개 경기의 layer0 사망 능력치 0x2A ADD 294건은 자원 0x0A ADD와 플레이어별 시각·값 순서가 전부 같았다. 다만 위 0x0431 비교는 최근접 비교이며 영상으로 확인한 일대일 사건 정답은 아니다. 두 신호를 같은 순간으로 취급하면 안 된다는 근거로 사용한다.

## 경기 결과와의 대조

기존 결과 화면 기록과 비교했고 M1의 실제 결과 이미지도 직접 확인했다. 아래는 보정하지 않은 ADD 합계의 비교다. 경기 종료 뒤 기록, 불완전한 리플레이, 결과 기록 자체의 오류 가능성을 포함한다.

| 후보 자원 | 비교한 결과 항목 | 동일한 플레이어 행 |
|---|---|---:|
| 능력치 `0x29` layer0 ADD | 킬 | 101/107 |
| 능력치 `0x2A` layer0 ADD | 사망 | 101/107 |
| `0x0B` 증가 | 어시스트 | 100/107 |
| `0x0E` 증가 | 미니언 처치 | 69/87 |

이 표는 의미를 좁히는 근거이며 전체 정확도를 보증하는 점수가 아니다. 합계 일치는 각 사건의 의미나 시각을 독립적으로 입증하지 못한다. 특히 미니언 처치는 불일치가 남아 있어 완성됐다고 보고할 수 없다.


## 실제 코드에서 고친 부분

새 타임라인 CLI와 기존 KDADetector 모두 레코드 경계를 따라 읽도록 했다. 기존 계산기의 다음 레코드 시각 참조와 30분 상한을 제거했고, 마지막 레코드도 독립적으로 읽는다. 메시지 안에 우연히 들어 있는 비슷한 바이트를 사건으로 잘못 잡지 않는다. 어시스트 후보 기록에는 자원 번호, SET/ADD 표시, 자기 시각과 전체 payload를 추가로 보존한다.

실제 56개 리플레이를 수정 전후로 비교했다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 킬 후보 | 2,192 | 2,192 |
| 사망 후보 | 2,165 | 2,209 |
| 미니언 후보 | 46,163 | 46,163 |

추가된 사망 후보 44건은 모두 30분 이후다. 시각이 없던 킬 후보 41건도 모두 30분 이후의 자기 시각을 되찾았다. 기존 사망 후보 한 건은 다음 시각 32.69308초에서 자기 시각 32.58894초로 바로잡혔다. 기존 킬의 식별 위치, 어시스트에 쓰던 eid/value/offset 조합, 미니언 후보는 동일했다.

이는 누락과 위치 오류를 고쳤다는 결과다. 추가 후보를 모두 실제 사망으로 독립 확인했다는 뜻은 아니다. 경기 종료 필터와 500바이트 이웃을 이용한 어시스트 추정 정책도 아직 남아 있다.

전체 257개 테스트가 통과했다. 신규 타임라인의 실제 M1 CLI에서도 레코드 위치와 자기 시각을 확인했다. 기존 헤더 상수를 사용하는 분석 도구의 import 호환성도 복구하고 회귀 테스트했다. 새 번역 필드와 최종 전체 검증 결과는 별도 검증 기록에 남긴다.

## 남은 증거를 정확하게 좁혔다

모든 이벤트를 해독했다고 말할 수는 없다. 남은 것은 막연한 추측이 아니라 다음 자료다.

- 아직 이름이 확인되지 않은 자원 9·10과 다른 번호, 상태 3·4 및 마스크 비트의 의미를 연결할 근거. 킬·사망·어시스트의 위 세 필드 매핑은 완료했다.
- 사건이 하나씩 구분되는 플레이 영상/기록 쌍: 사망 발생, 상태 전환, 부활을 구별한다.
- 동일 입력과 빌드에 대한 VGNA 중간 결과: 두 구현의 차이를 사건 단위로 비교한다.

확보된 경기별 정답은 결과 스크린샷과 truth JSON이다. 추가 로컬 영상 검색에서는 방송 대기 화면 1개와 현재 없는 경기 녹화 파일 4개의 편집 프로젝트 참조를 찾았으며, 실제 경기 영상은 확보하지 못했다. YouTube 채널 Sylaz Entaris도 탐색하려 했지만 저장된 사이트 접근 차단이 권한 변경 후에도 남아 있어 목록을 읽지 못했다. 사건별 영상 검증과 부활 시점은 미확인으로 남긴다.


## 실제 실행 코드 확인 방법

1.73GB짜리 IPA 전체를 받지 않고, 서버의 HTTP Range 기능으로 ZIP 목차와 게임 엔진 항목만 읽었다. 받은 자료는 총 15,777,593바이트, 추출한 엔진은 26,503,168바이트다. ZIP CRC가 일치했고 실행 코드의 암호화 표시는 0이었다. 설치하거나 실행하지 않고 정적으로 검사했다.

엔진 SHA256: `c23b2e9eb201f47694c7e71ab39d2c8c96850beb4ddf489745def23927fcd891`

| opcode | 실제 수신 처리 함수 |
|---|---|
| 0x0431 | 0x1003d451c |
| 0x041C | 0x1003db808 → 0x1003db80c |
| 0x041D | 0x1003dba48 |
| 0x042B | 0x1003dcc0c |

생성자와 송신 opcode 상수, 수신 큐의 가상함수 호출, 해당 처리 함수의 분기를 함께 확인했다. 주소가 우연히 같은 것만으로 일치 판정을 내리지 않았다. [VG:NA 커뮤니티 배포 사이트](https://client.vgna.net/)의 현재 배포 엔진에서 검증한 범위이며, 전체 게임 빌드 동일성이나 모든 enum 이름을 뜻하지 않는다.

## 판독기 사용

```sh
python -m vg.analysis.event_timeline "경로/경기.0.vgr" --entity 1500
```

실제 M1 출력에서 151.918초 기록은 `native_stat=deaths`, `native_operation=add`, `native_layer=0`, `value=1.0`으로 나온다. 153.756초 기록은 `native_type=actor_state_transition`, `native_state_from=3`, `native_state_to=4`로 구분된다. 각 행은 원본 위치·전체 payload와 검증 엔진 식별값도 담는다. 프레임이 잘못됐거나 원본 파일을 출력으로 덮어쓰려 하면 오류로 종료한다.

기존 KDADetector는 비교를 위해 남겼고 프레이밍 오류를 수정했다. 새 native 필드 해석을 기존 최종 통계 정책 전체에 자동 적용한 것은 아니다. 초기 상태, 누락과 경기 종료 시점을 확인해야 최종 KDA로 승격할 수 있다.

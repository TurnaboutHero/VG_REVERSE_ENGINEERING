# 오프라인 이벤트 검증과 0452 후속 조사

분석일: 2026-09-09. 디코더 기준 커밋: `018dfd227abc704ad3c281bacd9b203af2d2e108`.
이 문서는 [이전 종료 시점 카운터 감사](TERMINAL_COUNTER_AUDIT_2026-09-09.md)의 후속 연구다. 공개본은 개인 경로·계정 식별자·원본 payload를 제거한 파생 자료이며, 게임 내 최종 수치 검증이나 집계 정책 변경을 뜻하지 않는다.

게임을 실행하지 않아도 opcode의 데이터 구조와 실행 파일의 처리 경로를 검증할 수 있다. 게임 실행은 실제 행동·화면·최종 수치와 연결할 때 필요하다. 실행 여부만으로 모든 opcode의 모든 필드가 확정되지는 않는다.

## 코드별로 알 수 있는 범위

| 코드 | 현재 확인한 의미 | 별도 확인이 필요한 것 |
|---|---|---|
| `0430` | `ActionActorDie`, 사망 개체와 원시 사망 원인 참조 | 최종 킬 인정 대상, 스킬·피해 유형, 최종 데스 반영 여부 |
| `041c` | 능력치 SET/ADD. index 41/42는 킬/데스 | 해당 증가가 어떤 행동의 결과인지, 결과 화면의 확정 시점 |
| `041d` | 자원 SET/ADD. index 11은 어시스트 | 다른 자원 이름·획득 이유·경제 규칙 |
| `040b` | `ActionEntityDestroy`, 개체 제거 | 제거 이유와 사망·처치·보상의 관계 |
| `03f1` | `ActionEndMatch`, 승리 팀 필드와 종료 사유. 사유 2는 항복 | 큐 적용 시점, 최종 결과 표시와 모든 종료 사유 |
| `0452` | 이번에 확인한 `LevelControllerOnEnterPostGame` 콜백 호출 분기 | 서버 집계 중단 원인, 정확한 화면 전환 시각, 보편적인 최종 집계 기준 |

하나의 opcode가 하나의 게임 행동만 뜻하지 않을 수 있다. 예를 들어 `0430`은 영웅·미니언·구조물 모두에 나타나고, `041c`는 index와 연산 값에 따라 다른 능력치를 변경한다. 그래서 코드, 필드, 개체 종류, 기록 순서와 시각을 함께 확인한다.

## 이번에 새로 확인한 종료 전 신호

C16의 미대응 사망과 C02의 정상 기록을 원본에서 비교하다가 `0452`를 찾았다. 이후 원본 56개 기록 전체, 7,870개 구간과 30,729,156개 레코드를 다시 순회했다. 입력 해시는 기존 감사 자료와 일치했고 재검사 후에도 유지됐다.

- `0452`는 50개 기록에서 각각 한 번 나타났다. 관찰한 payload는 모두 6바이트의 `00`이었다.
- 기존 미대응 플레이어 사망 39건은 모두 `0452`보다 순서와 기록 시각이 뒤였다. 시각 차이는 약 0.209~5.901초였다.
- `0452`가 있는 기록의 정상 대응 사망 2,026건 중 2,025건은 신호보다 앞섰고, C16의 한 건은 순서상 뒤지만 같은 기록 시각이었다.
- `048d`는 `0452`보다 약 5.987~6.132초 뒤에 있었다. 이 차이는 기록 시각 기준이며 보편적인 6초 규칙은 아니다.
- `0452`가 없는 기록은 C09·C10·C33·C34·C38·C41이다. 이 중 앞의 다섯 기록은 종료 사유 2인 항복 기록이고, C41은 종료 액션이 없으며 기존 시계 판정도 mixed_segments다. C38은 기존 M6에 해당하므로 이 신호를 M6에 임의로 만들어 적용할 수 없다.

마지막 갱신 하나만 비교하는 오류를 피하기 위해, 56개 원본을 별도로 다시 순회해 모든 선택 플레이어의 킬·데스·어시스트·resource 14 연산을 직접 검사했다. 총 54,170건이며 SET/ADD와 비영(非零) 계층도 검사 대상으로 포함했다. 실제 관찰은 모두 ADD였고 능력치 계층은 0이었다. 선택 플레이어 통계의 미지원 payload 길이는 없었다.

`0452`가 있는 50개 기록에서는 49,748건이 신호보다 순서·시각 모두 앞섰고, 14건은 순서상 뒤지만 같은 시각이었다. 기록 전체에서 신호보다 엄격히 늦은 기록 시각의 점수 연산은 0건이었다. 나머지 4,408건은 `0452`가 없는 여섯 기록에 있어 이 신호와의 관계를 부여하지 않는다. 이 관찰은 서버 원인이나 최종 화면의 정확성을 증명하지 않으며, resource 14의 이름도 검증된 킬·데스·어시스트와 구별한다.

## 신호 직후를 잘라내면 틀리는 반례

C16에서는 아래 레코드가 모두 같은 기록 시각 `1697.6822509765625`에 있다. 순서는 파일의 전역 0 기반 인덱스다.

| 순서 | 레코드 | 확인한 내용 |
|---:|---|---|
| 717170 | `0452` | 경기 후 상태 진입 콜백 신호 |
| 717171 | `0430` | 플레이어 1506 사망 |
| 717175 | `041c` | 플레이어 1506의 데스 ADD 1 |
| 717181 | `041c` | 플레이어 1504의 킬 ADD 1 |
| 717185 | `041d` | 플레이어 1500의 어시스트 ADD 1 |
| 717189 | `0430` | 정의 이름이 `VainCrystal_Away_5v5`인 개체 2007의 사망 |

이후 `1699.3516845703125`의 플레이어 1504 사망에는 대응하는 데스 증가가 없다. 더 뒤의 스냅샷도 기존 데스 값 7을 유지한다. 따라서 이 사례는 더 이른 경기 후 단계와의 관계를 조사할 근거가 되지만, `0452` 이후 레코드를 일괄 버리는 규칙은 위 정상 증가를 잃게 된다.

C02는 마지막 15초에 플레이어 사망이 없어 플레이어 데스의 정상 대조군으로 충분하지 않다. 대신 신호 후 플레이어를 원시 source로 가진 미니언 사망 6건이 있고 resource 14 갱신은 없다. 다만 원시 source가 최종 처치 인정 대상임을 보장하지 않으며 resource 14의 화면 이름도 별도 검증 범위라서 이를 “CS 6개 누락”으로 확정하지 않는다.

## 실행 파일에서 확인한 동작

검사한 Windows 실행 파일의 SHA-256은 `659f9eed557a426db57554d2a768efe34ba9fe02ba1085d77db64390b0d92642`다. 파일과 Ghidra 프로젝트의 해시를 대조하고 프로젝트를 읽기 전용으로 열었다. 기계어는 LLVM 디스어셈블리로도 확인했다.

`004cfec0`의 `0452` 분기는 한 바이트를 읽은 뒤 `method_onPacket_LevelControllerOnEnterPostGame`이라는 키로 등록된 콜백을 찾아 호출한다. 확인한 등록 대상은 `KindredHUDQuickMessageMenuMC`이며, 콜백 `006f0b10`은 그 컨트롤러의 `+0x18` 플래그에 `3`을 OR한다. 해당 경로에 데스 카운터를 직접 쓰는 코드는 없다. 다른 동적 등록, 서버 통계 생성과 모든 콜백 부작용을 확인한 것은 아니다.

기록별 생산 빌드가 이 실행 파일과 모두 같다는 점, 콜백이 실제로 실행됐는지, 화면의 최종 KDA는 아직 독립 확인이 필요하다. 지원되지 않는 시계와 mixed 기록의 기존 판정도 유지한다.

## 근거와 재현 범위

공개 근거는 [56개 기록별 집계](evidence/2026-09-09-postgame/corpus-summary.json), [39건 사망·14건 동일 시각 갱신과 대조 사례 위치](evidence/2026-09-09-postgame/record-locators.json), [native 처리 경로](evidence/2026-09-09-postgame/native-evidence.json), [제한된 기계어 발췌](evidence/2026-09-09-postgame/native-instructions.txt)에 있다. 기록의 숫자 개체 참조는 해당 기록 내부 식별자이며 계정 정보가 아니다. 시각은 원시 record envelope 값이다. C30·C52의 unsupported와 C41의 mixed_segments 판정을 유지하므로 그 원시 시각 관계를 검증된 게임 시계로 승격하지 않는다.

[출처·변환·파일 해시](evidence/2026-09-09-postgame/provenance.json)는 비공개 원본 분석 자료와 공개 파생 파일의 SHA-256을 별도로 기록한다. 두 파일의 해시는 변환 때문에 달라진다. 원본 리플레이, 개인 경로, 플레이어 이름, 실행 파일 및 전체 디컴파일은 포함하지 않는다. 섹션 목록은 기록별 canonical JSON 해시로 묶었으므로 공개본 자체가 7,870개 원본의 재검사를 대신하지는 않는다.

저장소 루트에서 아래 명령으로 공개 자료의 집계·위치 관계·해시·문서 링크를 확인할 수 있다. 원본을 재분석하거나 게임을 실행하는 명령은 아니다.

```sh
python vg/docs/evidence/2026-09-09-postgame/verify.py
```

원본 보유자가 전체 분석을 재현하려면 다음 절차가 필요하다.

1. 같은 순서의 56개 입력과 원본 섹션 해시를 준비하고, 기준 커밋의 `iter_records`로 모든 구간을 다시 순회한다. 전역 0 기반 순서·섹션 번호·바이트 위치·원시 기록 시각을 보존한다. 재순회 전후 해시를 비교한다.
2. `03ef`·`03f0`·`0452`를 전체 구간에서 추출한다. 이전 감사의 유일한 1:1 동일 시각 대응과 사망 이후 100ms 안의 유일 대응 규칙을 그대로 사용해 사망/데스 증가 대응을 가져온다. `0452`가 없는 기록에는 관계를 부여하지 않는다.
3. 별도의 전체 순회로 선택 플레이어 `041c` index 41/42와 `041d` index 11/14의 SET/ADD 및 모든 능력치 계층을 선택한다. 미지원 선택 플레이어 통계 길이를 따로 집계하고, 모든 연산을 `0452`와 순서·시각 두 축으로 직접 비교한다. 마지막 연산만 비교해서는 더 이른 순서의 늦은 시각을 배제할 수 없다.
4. 동일 해시의 Windows 실행 파일을 읽기 전용으로 분석하고 공개 native 주소를 대조한다. 콜백 키를 FNV-1a32로 계산해 `07b2a736`인지 확인한다. 이 단계도 각 기록의 생산 빌드 일치를 입증하지 않는다.

비공개 스캐너와 원본 자료의 해시는 provenance에 남긴다. 이 공개 패키지만으로 원본 전체 순회의 독립 재현은 불가능하며, [검증 스크립트](evidence/2026-09-09-postgame/verify.py)는 공개 변환 결과의 내부 일관성을 확인한다. 디코더의 최종 통계 정책은 변경하지 않았다. 게임 및 결과 화면 검증도 이 오프라인 연구에 포함되지 않았다.
